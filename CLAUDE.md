# Archnexus Toolbox

Internal web tools for Archnexus, an ~80-person architecture firm. One web app ("the Toolbox") with a sidebar; each tool is a module: **Scheduler**, **Fee Builder**, **Minutes**, with more to come. The owner is Josh: an architect moving into the CFO role, not a software developer. Kent, the firm's IT lead, will host it on the firm intranet later and will probably rebuild the front end.

This repo is the working prototype. It runs **only on Josh's computer** (localhost) until Kent's server exists. Its lasting value is the behavior, data model, business rules with tests, the platform contract and the design system. The screens are prototypes that define behavior and look.

## Decisions already made (do not reopen without Josh)

- **One app, one database**: shared core tables (people, projects, project teams, access overrides, firm settings) plus tables per module. A new module adds its own tables and only reads the core ones.
- **Sign-in in production**: the firm's network (Windows domain) username and password. **Locally**: a "sign in as" picker of seeded test users. No real authentication code.
- **Vantagepoint (VP)**: projects, employees and project teams are copied nightly into the Toolbox's own tables. Locally, the same tables load from CSV files (seeded with made-up data).
- **Live updates**: polling every 15–30 seconds is acceptable. No WebSockets.
- **Record ids**: generated by the app as text (UUID-style) until Kent decides otherwise.
- **Permissions**: the rule already exists as a pure, tested function in the Scheduler (`effectiveAccess`, `canDo`, `canDeny`, `canDuplicate`). It moves to shared code and the **server** enforces it. The browser only hides controls.

## Architecture

```
server/             Node server: API + static files. Binds to 127.0.0.1 only.
  db/               schema.sql, migrations, seed data (CSV), the SQLite file (git-ignored)
shell/              sign-in-as picker, sidebar, routing (#/scheduler/...), theme and density, project picker
shared/
  design-system/    copied from design-system/project: tokens, bundle.css, bundle.js, fonts (generated CSS, see below)
  platform/         THE ONLY CODE THAT TALKS TO THE SERVER: Session, Directory, Store, Files, Locks
  rules/            permission rules (from the Scheduler), shared helpers
modules/
  scheduler/  fee-builder/  minutes/
    logic/          pure business rules, no DOM, no network
    ui/             screens
    tests/          unit tests + fixtures/*.json (language-neutral input → expected output)
docs/               PLAN, CONTRACT, AUDIT, DECISIONS, one SPEC per module
design-system/      the design system source (master copy, see "Design system")
reference/          existing apps, read-only
```

- **Front end:** plain JavaScript ES modules served as files, no framework and no build step unless a phase proves one is needed. The existing apps are vanilla JS; keep it that way so porting stays mechanical.
- **Server:** Node (LTS) with SQLite. Prefer the built-in `node:sqlite` if the installed Node supports it, else `better-sqlite3`. Keep dependencies few. Write SQL that would port to SQL Server or PostgreSQL: no SQLite-only tricks.
- **Module records:** each module's records live in a generic `records` table (module, collection, id, project_id, rev, data as JSON, created/updated by and at, deleted flag). Core data (people, projects, teams, access) gets real columns. This keeps adding modules cheap. Record the reasoning in `docs/DECISIONS.md` for Kent.
- **API shape** (see CONTRACT §5 and §8): `GET /api/me`, `/api/people`, `/api/projects`, `/api/projects/:id/team`, `GET /api/:module/:collection?since=<ms>`, `GET|PUT|DELETE /api/:module/:collection/:id` with `If-Match: <rev>` (409 on mismatch), `/api/backup` export and import, `POST /api/admin/import-vp` (CSV).

## Rules

1. **Platform calls only in `shared/platform/`.** Modules never call `fetch`, `localStorage` (except per-device preferences through `pref()`), or anything server-side directly.
2. **Business logic is pure and tested.** No DOM or network in `logic/`. Every rule worth having gets a fixture in `tests/fixtures/` (JSON input and expected output), so the tests stay usable if the rebuild is in another language.
3. **Existing tests must keep passing** when a module is ported. A failing reference test means the port is wrong, not the test.
4. **Design system:**
   - Use tokens and the shared classes.
   - No hex colors or raw `nx-*` values in module CSS.
   - Module-specific CSS lives in the module and uses tokens only.
   - Run `python3 design-system/tools/audit.py` on a built page when a module's look changes.
   - The repo's `design-system/` is now the master copy; the published "Arch Nexus Toolbox" design-system artifact is a view of it that Josh refreshes.
5. **Record rules** from CONTRACT §2: `schemaVersion`, `rev`, `createdAt/By`, `updatedAt/By` on every top-level record; store ids, not names; projects carry `vp: { projectId, number }`.
6. **Data safety:**
   - Bind to 127.0.0.1.
   - Never commit the database file or any real firm data (client names, fees, minutes).
   - Seed data is made up.
   - If Josh wants to load real data, he says so explicitly and it stays out of git.
7. **Don't build what production replaces:** no real login, no user management screens, no deployment scripts for the intranet.
8. **Work in phases** (`docs/PLAN.md`):
   - Finish a phase.
   - Run all tests, then open the app in a browser and click through what changed.
   - Commit.
   - Stop and give Josh a short plain-language summary: what works, how to try it, what is open.
9. **Commits:** small, descriptive, on a branch per phase; merge to `main` when Josh has looked. Never force-push.
10. **Decisions:**
    - Product decisions (how a feature should behave) are Josh's: ask, with a recommendation.
    - Technical decisions inside these rules are yours: make them and record the non-obvious ones in `docs/DECISIONS.md`.
11. **Talking to Josh:** plain language, short, no jargon without a one-line explanation. He wants honest assessments, not reassurance. Say what you did not test.

## Commands

On Windows PowerShell, type `npm.cmd` instead of `npm` (PowerShell blocks the `npm` script).

- `npm start`: run the Toolbox at http://localhost:5280
- `npm test`: all unit tests (server, shared, every module)
- `npm run seed`: reset the local database to the seed data
- `npm run backup`: write a full backup JSON to `backups/` (git-ignored)
- `node design-system/tools/build_css.js`: regenerate `shared/design-system/` after changing `design-system/project/`
