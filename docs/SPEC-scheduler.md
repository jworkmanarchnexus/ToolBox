# Spec: Scheduler

What the Scheduler does and must keep doing, for whoever rebuilds the screens. Behavior, data, permissions and what is still open. The business rules are in `modules/scheduler/logic/` (pure code) with language-neutral fixtures in `modules/scheduler/tests/fixtures/`; the screens in `modules/scheduler/ui/` are a prototype that defines behavior and look.

Longer background (kept as written, still accurate unless this page says otherwise): `reference/source/scheduler/toolbox-handoff/SPEC.md` (the original handoff spec, sections 1 to 16), `docs/EDITOR-FEATURES.md` and `docs/DATA-SCHEMA.md` in that folder.

## 1. What it is

Project schedules for an architecture firm: a list of activities and milestones with dates that recalculate when something they depend on moves (like MS Project, but much lighter). Many people work in one project's schedules; each saves for everyone. Dates are calendar days. Weekends and holidays are shown and flagged, but durations and links count calendar days (so a date never moves on its own because of a calendar setting).

Not in scope: resource leveling, cost, percent complete, Gantt printing beyond the exports, real-time cursors, autosave (saving is deliberate: review, then Save).

## 2. Pages

| Page | What it does |
|---|---|
| Scheduler home | Projects the person can see (active; archived collapsed). Search, "My projects" (on the Vantagepoint team) or all, filter by has-a-schedule, sort. Each row opens the project's primary schedule or offers New schedule. |
| Project page | The project's schedules, the primary one starred and first, the team and the person's access. New schedule, Duplicate, Open. |
| New schedule | Pick a template (company, personal, or blank), a start date and the length of each phase in weeks; see the resulting dates before creating. The project is required. |
| Editor | Table view, Timeline (Gantt) view, optional Executive view. See section 4. |
| Templates | Company templates (starters plus the firm's own) and My templates. Managers edit company templates. Edit a template in the same editor. |

## 3. Data

All records are in the Toolbox's generic store, module `scheduler`; each carries the envelope fields (`rev`, `schemaVersion`, `createdAt/By`, `updatedAt/By`) set by the server. Task ids are text, generated by the editor.

| Collection | Record | Notes |
|---|---|---|
| `schedules` | One schedule: name, tasks, scale, colors, holidays, working days (`offDays`), project details (`info`), baseline, executive settings, shared export settings, commitment margin | Linked to its project (`projectId`). Schema: `docs/schedule.schema.json` in the source handoff. |
| `h-<scheduleId>` | One saved version of that schedule | Newest 40 kept; saves by one person within ten minutes share an entry. Same project link. |
| `project-settings` | `{ primaryId }`, id `ps-<projectId>` | Which schedule is the project's primary. |
| `firm-holidays` | The firm holiday list | Firm admins write. A schedule starts from it and then keeps its own list. |
| `firm-templates` | Company templates; a starter template that was edited is stored here as `starter_<id>`; a removed starter is a hidden marker | Firm admins and template managers write. |
| `firm-writers` | `{ ids }`, id `firm-templates`: the template managers | Firm admins write. |
| `personal-templates` | A person's own templates | Only that person can read or write them. |

A task: `id, name, kind (task | milestone), duration (calendar days; 0 for a milestone), start (ISO date), locked, notBefore (a hold), deps [{ id, type FS | SS, lag days }], ignore [flag codes], lvl (client | design | internal), exec, exColor, commit {date, note}`.

## 4. The editor: behavior that must be kept

The checklist is `docs/EDITOR-FEATURES.md` in the source handoff. In short:

- **Cascade.** A task with predecessors starts at the latest of what they imply (finish-to-start, start-to-start, each with a signed lag), never before its own hold (`notBefore`); an unlocked task's stored start is recomputed. A locked task keeps its date and shows a conflict if predecessors would push past it. Milestones sit on one date. Loops are detected and flagged on both tasks. Fixtures: `cascade.json`, `predecessors.json`.
- **Flags** (the Issues panel): starts or finishes on a non-working day, a milestone on one, a lock conflict (with a one-click suggested date), a loop. A person may "ignore" a flag per task.
- **Editing** in the table: name, type, audience, executive tick, start, days, finish (changing it changes the duration), predecessors typed as row numbers ("3", "5SS+2"), lock. Dates are typed freely ("10/15", "Oct 15"). Add, insert-and-link, delete, move, multi-select, drag to reorder, drag bars and link handles in the timeline. Undo up to 60 steps. Every change explains its effect ("12 activities moved 14 days; the commitment is now 3 days late").
- **Commitments.** A task or milestone may carry a committed date; the forecast is compared with it: on target, early, late, or at risk inside the project's margin setting. Fixture: `commitments.json`.
- **Baseline and slip.** Snapshot every task's dates; each task then shows how far its finish has moved.
- **Audience levels** (client, design team, internal) and the executive overview control what each export shows.
- **Saving.** Deliberate. A save sends the version it started from; if someone saved in between, the server refuses and the editor merges the other person's changes into the person's unsaved ones and asks them to review (and to choose where both changed the same thing). Never a silent overwrite. Fixture: `merge.json` (21 cases). A save also writes a history entry.
- **Presence.** While a schedule has unsaved changes the person holds a short lock; others see "X is editing". Informational: the real protection is the save check.
- **Exports.** PDF, PNG, Excel and CSV, by audience, with shared per-project defaults and per-device settings. PNG and PDF are drawn in the browser (canvas, jsPDF).
- **Duplicate.** Into any project the person can edit, keeping dates or shifting every date by the same number of days; history and baseline are not copied; commitments are copied only inside the same project and never shifted. Fixture: `duplicate.json`.
- **Templates.** Phases run Monday to Friday, in whole weeks; choosing a phase length moves everything after it by exactly the difference. The starter library and the dates it produces are pinned in `starter-templates.json`.
- **Holidays.** US federal holidays (plus Utah's Pioneer Day) with Saturday/Sunday observance. Fixture: `holidays.json`.

## 5. Permissions

Permissions belong to the project, not the schedule. Computed on the server for every call by `shared/rules/permissions.js` (fixtures: `shared/rules/tests/fixtures/permissions.json`):

- A firm admin is admin everywhere.
- A manual **deny** beats everything else except firm admin.
- PIC, PM or PA on the Vantagepoint team: admin on the project (edit, and manage who has access).
- Anyone else on the team: read. A manual grant adds viewer or editor. A firm viewer reads every project.
- An archived project is read-only for everyone; only a firm admin can delete there.
- Duplicating needs read on the source and edit on an active destination.
- A project admin cannot deny another lead or themselves; only a firm admin can.

Template permissions: starters and company templates are read by everyone; firm admins and the listed template managers change them; each person's own templates are private to them.

## 6. What is not built, or is different from the old prototype

- Projects are not added or edited in the Scheduler: they come from Vantagepoint (the nightly copy). A schedule needs a project; "unassigned" schedules cannot be created.
- The "Here now" chips show editors (people holding a lock), not everyone who has the page open.
- The server does not write history in the save transaction; the editor does, afterwards (a failed history write never blocks a save).
- Changes by others arrive by polling (about every 20 seconds), not instantly.
- The Scheduler loads all schedules the person can see into the page and filters there. Fine at the firm's size; at hundreds of schedules, list per project.

## 8. Tests

`npm test` runs: the original engine, merge and module suites at their baseline counts (53, 80, 199), the fixture runners (`cascade`, `merge`, `rules-fixtures`), and interface tests that drive the real screens against a real server (`integration.test.js`). Canvas exports (PNG and PDF) are checked by hand in a real browser; end-to-end browser scripts from the prototype were replaced, not ported (docs/DECISIONS.md, Phase 2).
