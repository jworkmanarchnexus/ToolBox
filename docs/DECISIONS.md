## Phase 1 decisions (2026-10-11)

- **Records table.** `records(module, collection, id, project_id, rev, schema_version, data JSON, created/updated at and by, deleted)`. One table serves every module, so a new module needs no schema change. Kent can keep it, or turn each collection into real tables when he rebuilds (the JSON shapes are in each module's SPEC). Core data has real columns.
- **Envelope.** The API returns `{ module, collection, id, projectId, rev, schemaVersion, createdAt, createdBy, updatedAt, updatedBy, deleted, data }`. The CONTRACT section 2 fields live in the envelope, not inside `data`; the module only supplies `data.schemaVersion`. The server owns `rev` and the stamps, so a module cannot forge them.
- **Compare-and-set.** `PUT` with `If-Match: <rev>`; creating needs no header; an existing record without one gets 428; a stale one gets 409 with the stored record in `current`. `DELETE` is a soft delete (needs `If-Match` too) so other people's polls see the tombstone.
- **Polling cursor.** `GET .../:collection?since=<ms>` returns records with `updated_at > since` (including deleted ones) plus `serverTime`. The server clock is strictly increasing, so two writes in one millisecond are never missed (tested).
- **Who may touch a record** (`server/records.js`):
  - Has a `projectId`: the shared permission rule decides (view, create, edit, delete); archived projects are read-only.
  - No project and collection `personal-*`: only the person who created it.
  - No project and collection `firm-*`: everyone reads, only firm admins write.
  - No project, any other name: everyone reads; the creator or a firm admin writes.
  - **This is my assumption.** Phase 2 and 3 will test it against real needs (templates, holidays, pursuit proposals).
- **A project you cannot see returns 404**, not 403, so existence is not leaked.
- **Sign-in as (local only).** The browser sends `X-Toolbox-User: <person id>`; `/api/dev/users` lists the test people. This is a stand-in for the network sign-in and has no security value. Do not expose the server beyond 127.0.0.1.
- **Firm roles** (`admin`, `viewer`) live on `people.firm_role`, loaded from `server/db/seed/firm_roles.csv`, because Vantagepoint does not hold them. The `import-vp` endpoint never touches them.
- **VP import.** `POST /api/admin/import-vp?kind=employees|projects|team` with the CSV as the body (firm admins only). Order matters: employees, projects, team. The team file replaces the team of every project it mentions, like a nightly copy would. A project whose status is not "Active" becomes archived. CSV columns are in `server/db/seed/`; **they are my guess at a VP export** and should be checked against the real export.
- **Backup.** `GET /api/backup` (full: core tables and every module) or `?module=x`; `POST /api/backup` imports. Firm admins only. Import is additive and reports what it skipped. The CONTRACT says personal data exports only for the person exporting; the admin backup includes it, because a full backup that drops data is not a backup. Revisit if that matters.
- **Locks** last 45 s and are refreshed by the editor every 15 s. They are advisory; compare-and-set is the real protection.
- **No project create or edit API.** Projects arrive only through the Vantagepoint copy. The CONTRACT's `Directory.createProject` is not built; add it only if a module needs hand-entered projects locally.
- **Design system CSS** is generated by `design-system/tools/build_css.js`, a Node port of the Python script (output verified identical). `shared/design-system/` is committed and a test fails if it goes stale.
- **`shared/platform/package.json`** sets `"type": "module"` so the same files run in the browser and in Node tests.
- **Windows PowerShell blocks `npm`** (script execution policy). Use `npm.cmd`, or Command Prompt, or Git Bash.

## Phase 2 decisions: Scheduler (2026-10-11)

- **The bundle.** The Scheduler was written as one shared scope (about 25 files reach across each other's top-level names). Rewriting that into ES modules would have been a large rewrite with no behavior gain, so `tools/build.js` concatenates the files listed in `modules/scheduler/bundle.json` into `modules/scheduler/dist/scheduler.js` (and the stylesheets into `scheduler.css`). `dist/` is generated and git-ignored; `npm start` and `npm test` build it first. This is the "build step a phase proves is needed" in CLAUDE.md. Fee Builder and Minutes already build to one file, so they use the same tool.
- **Engine and rules are untouched.** `engine.js`, `merge.js`, `templates.js`, `commit.js`, `impact.js` and `dup.js` are byte-identical to the redesign source (checked with `cmp`). `permissions.js` is `shared/rules/permissions.js`, also identical. Baseline counts are held by `modules/scheduler/tests/baseline.test.js`: 53, 80, 199.
- **One data-layer file.** `modules/scheduler/ui/store.js` is the only Scheduler file that talks to the platform; the shell hands it the adapters (`Session`, `Directory`, `Store`, `Locks`, `Files`). A test (`server/tests/rules.test.js`) fails if any module source calls `fetch`, `localStorage`, `indexedDB` or `window.claude`.
- **What replaced what.**
  - Live snapshots became polling (about 20 s, `shared/platform/store.js`). Names come from the directory, never from records.
  - The save-id check became compare-and-set on `rev`. A 409 carries the stored record, which goes into the existing three-way merge dialog.
  - Presence became locks: a person holds a lock on the schedule while it has unsaved changes. "Here now" therefore shows editors only; it no longer shows people who merely have it open.
  - The hand-entered project list became the Directory (read-only). **Add project, Project details and "Unassigned" creation are gone** (projects come from Vantagepoint). Project access (`read`, `write`, `admin`) drives which buttons show.
  - Personal templates became `personal-templates` records. Company templates are `firm-templates`; template managers are the record `firm-writers/firm-templates`, which the server consults (see `isWriter` in `server/records.js`).
  - A project's primary schedule is a record in `project-settings` (id `ps-<projectId>`), because projects themselves are read-only.
- **History** is one record per saved version, in a collection per schedule named `h-<scheduleId>` (linked to the schedule's project, so it follows the same permissions). The client still merges saves by one person within 10 minutes and keeps the newest 40, as before. The server does not write history in the same transaction as the save (PLATFORM-SEAM suggests that); Kent can move it server-side.
- **Ids.** Schedules and history entries use 32 hex characters from `crypto.getRandomValues` (works on plain http, unlike `randomUUID`). Starter templates have short ids ("fed"), so their company copies are stored as `starter_<id>` (the server needs 6 or more characters).
- **Self-hosted libraries.** `xlsx`, `jspdf` and `jszip` (same versions as before) are in `shared/vendor/`; nothing loads from a CDN. Fonts come from the shared design system.
- **Per-device settings** use `pref()` (`toolbox:sched.*` keys) instead of the old `schedsheet:*` keys, so existing browser settings do not carry over.
- **Module CSS.** `ui/tokens.css` holds the Scheduler-only tokens (bars, weekends, audience colors, older preset hues, dark overlays) and is the only module stylesheet allowed to contain hex colors. `editor.css` and `scheduler.css` use tokens only (checked by a test). Six dark tooltip and paper-preview colors that were hard-coded became tokens.
- **Mounting.** The shell loads the bundle on first use and keeps the module's pages alive while you visit other pages. Leaving with unsaved edits asks first (`isDirty`/`confirmLeave`). Switching user reloads the page so no state survives.
- **Not ported:** the three Python/Playwright end-to-end scripts (`e2e-export.py`, `e2e-legacy.py`, `e2e-templates.py`). They drove the old mock platform and file paths. Their server-touching coverage (create, save, merge, permissions, templates, managers) is rebuilt in `modules/scheduler/tests/integration.test.js`, which runs the real bundle in jsdom against the real server. Canvas drawing for PNG and PDF export cannot run in jsdom, so exports were checked by hand in a real browser: CSV, Excel, PNG and PDF each produced a valid file.
- **Found and fixed while porting:** a template opened before the managers list arrived showed "view only" and stayed that way, and a template edited by someone else did not refresh. Both existed in the original (they depended on snapshot timing); `tplChanged` now re-checks.

## Phase 3 decisions: Fee Builder (2026-10-11)

- **Same bundle tool as the Scheduler** (`modules/fee-builder/bundle.json`). The six engine files (`money`, `model`, `calc`, `analysis`, `exporter`, `sample`) are copied unchanged into `modules/fee-builder/logic/`; the 64 engine tests run unchanged (`tests/baseline.test.js` holds the count). Interface tests: 24 now, of which 14 are the original workflow tests with only the page start-up changed, 1 is the original page test adapted to the Toolbox shell, and 9 are new (saving, drafts, migration, conflicts, repair, linking and permissions, settings, backup). The original total was 85 (64 + 21).
- **Product decision for Josh (provisional): proposals before a Vantagepoint project exists.** CLAUDE.md says to ask. I built the option I recommend and kept the others open: a proposal starts **unlinked** (a pursuit) and stays visible only to its author, firm admins and firm leadership (firm viewers); it can be **linked** to a project later from Establish → Project → "Vantagepoint project". Once linked it follows the project's access: PIC, PM and PA edit it, the team reads it, nobody else sees it. If you would rather link pursuits to a Vantagepoint "promotional project", nothing changes in the code: that is just a project in the list. If you want pursuits visible to more people (a "sales team" or "all principals"), that needs a sharing rule that does not exist yet.
- **New server rule for fee data.** Collections named `owned-*` follow the project when linked and are creator-only (plus firm admins, and firm viewers read-only) when not. Fee proposals live in `fee-builder/owned-proposals`. This is deliberately stricter than the artifact, where everyone it was shared with saw every proposal. Tested in `server/tests/permissions.test.js`.
- **Revision.** The proposal's own `rev` counter is gone from the saved data; the server's revision (`If-Match`) replaces it. The existing conflict choice ("keep mine / load theirs") is kept; it now fires when the server answers 409, or when a poll shows someone saved while this window has unsaved edits.
- **Saving** still happens about 0.7 seconds after the last edit (debounced). Drafts for crash recovery are kept on this device through `pref()`, key `fb.draft.<id>`, the same as before in effect.
- **`schemaVersion`.** The server requires one on every record; Fee Builder sets it to its own `schema` number (3). Migration from v1/v2 still runs on load and writes back v3 with the original kept in `legacyOriginal`.
- **Personal settings** are `personal-settings/settings-<person id>`: private to the person, even from firm admins.
- **What the module no longer does:** the local-browser fallback store (`fb3.proposals`) and the artifact-only code path are gone; the Toolbox needs the server. The side bar, theme switch and tool links belong to the Toolbox shell. Fee Builder's own copy of the shared CSS (169 of 173 rules identical to the design system) and its 29 alias token names are removed; its chart series colors and a few brand marks are in `ui/tokens.css`, and `ui/styles.css` uses tokens only (checked by tests, together with a test that every variable used is defined).
- **Found while porting:** a link chosen in the page could be wiped by a background refresh arriving before the save went out. The refresh now ignores proposals with unsaved changes.
- **Not done:** the project link cannot be changed once a proposal is linked and the person lacks edit access to the original project (the picker is disabled; the server would refuse). The "number" and "client" typed fields are still free text and are only pre-filled from the project at link time.

## Phase 4 decisions: Minutes (2026-10-11)

- **Tests first.** The v16 zip shipped no tests, so `modules/minutes/tests/logic.test.js` (16 tests) characterizes the business rules in `logic.js` as they behave in the source: numbering and cadence, one open draft per series, assignments becoming numbered actions, carry-forward into the next agenda, publish blockers, moving due dates, locking after a later meeting, revising and cancelling a revision, attendance, state normalization, the two-device merge, backups and text output. They pass against the original code; the port then changed only one line of it (below).
- **One line changed in `logic.js`:** `createProject` now accepts an id, so a Minutes project can carry the Toolbox project's id. Nothing else in `logic.js` or `pdf.js` changed.
- **Same bundle tool** (`modules/minutes/bundle.json`). jsPDF is the shared copy in `shared/vendor/`, loaded when the first preview or PDF is made. The embedded PDF fonts, the logo for the PDF and the printed page's own CSS stay in the module as data files (`ui/assets-*.js`); the printed page's colors are part of the document design, not the app screens, and are kept as they were.
- **Sync keeps its rules; the server makes writes safe.** `logic.js` still decides what is newer and what conflicts, using `updatedAt` and the last-synced mark per record, so its tested merge is untouched. What changed is where records go: each write names the server revision it started from (`If-Match`), so two devices can no longer overwrite each other in the same instant. If the server says someone else wrote first, the record is compared with their copy exactly as a pull would compare it, and either goes ahead or is held in the existing "keep mine / use theirs" list. Pulls happen on start, on focus, and every 30 seconds while the page is open; "Sync now" still works. Editing offline, then reconnecting, sends everything (tested through the screens).
- **Projects come from Vantagepoint.** Minutes' own project list is gone. A Minutes project is a record keyed by the Toolbox project id; people who can edit a Vantagepoint project (PIC, PM, PA) see "Start minutes for a project" and pick one. The project's name and number are read-only and follow Vantagepoint (a rename shows up and is saved by the next project lead who opens Minutes). Everything Minutes keeps about a project (address, owner number, contacts, series, meetings, actions, issued copies, images) is linked to it, so the project's access rules apply: leads edit, the team reads, others see nothing (tested).
- **Per-project permissions replace the old single read-only switch.** On the home page, buttons for a series follow that series' project.
- **Firm settings** are the record `firm-settings/...`; only firm admins write them (the same rule as other `firm-*` collections), and the sidebar entry is a button on the home page for admins.
- **Local copy.** The IndexedDB / browser-storage / memory cache moved into the platform as `Cache` (`shared/platform/cache.js`), keyed by person, so a shared computer never shows one person another's data. A test checks the keys.
- **The example project** ("Load an example project") is now a private sandbox on this device: its records are never sent to the server (they have no Vantagepoint project to belong to).
- **Backups** use the Toolbox's common file format (`toolbox-backup`, app `minutes`); files from the earlier version still import. Importing records into a project you cannot edit is accepted locally and then refused by the server for that project only; the refused records are not retried.
- **Design system.** The Minutes stylesheet was already built on a copy of the shared tokens. 33 rules identical to the design system and 48 that differed (the shell, buttons, chips, banners, fields, tokens) were removed, so the shared versions apply; `btn pri` became `btn primary`. The 25 parallel token names (`--paper`, `--ink`, `--rule`, ...) were replaced by the design-system tokens, `ui/minutes.css` uses tokens only, and the few paper and brand marks it needs are in `ui/tokens.css`. The result looks almost the same as before, because the look was already the design system's; the visible changes are the Toolbox side bar and the sync status in the page header. Before and after screenshots: `docs/screenshots/minutes-*.jpg`.
- **Moving inside Minutes** (home, project, series, meeting) is still internal, not in the address bar, so the browser Back button leaves Minutes. Making those views routes (`#/minutes/...`) is a good follow-up.
- **Not tested here:** PDF output beyond "a valid PDF downloads and the preview draws" (checked by hand in a real browser: the agenda PDF is a valid 120 KB file and the four-page preview draws); photo attachments (the image-shrinking code is unchanged and needs a real browser); two people editing the very same record at the same instant over a slow network.

## Phase 5 decisions: handoff quality (2026-10-11)

- **Specs.** `docs/SPEC-scheduler.md`, `SPEC-fee-builder.md`, `SPEC-minutes.md`: behavior, data, permissions, what is not built, open questions, how each is tested. They start from the specs in the source zips (the Scheduler's SPEC.md, the Fee Builder's docs) and say where the port differs. Minutes had no spec; its page is the first written record, built from reading the code and the new tests, so check it against how people actually use it.
- **Fixtures** (language-neutral JSON, each with a description at the top saying how to read it):
  - Scheduler: `cascade` (9), `merge` (21 cases with full documents), `commitments` (8), `predecessors`, `holidays`, `starter-templates` (the library data and the dates it yields), `duplicate` (4), plus the permission fixtures from Phase 1.
  - Fee Builder: `calc` (15 whole-proposal cases, including the EAC and WSU workbook examples to the cent) and `rules` (typed numbers, rounding, contract value, back-solving).
  - Minutes: `dates-and-numbers`, `sync` (three decision tables), `carry-forward` (a four-meeting scenario in plain steps).
  Runners next to them (`*-fixtures.test.js` and friends) show how a fixture maps to code. Expected values come from three places, and the files say which: the original suites' assertions, workbook arithmetic written beside each case, and (for the starter templates and holiday list) the current engine's output pinned as a characterization. The pinned ones prove "unchanged", not "right"; review them.
- **Not turned into fixtures:** the Scheduler's change-impact wording, the Fee Builder's exports and snapshots, and Minutes' publish blockers. They are covered by tests that assert behavior in code (and described in the specs) but are tied to text or document structure that a port will redesign.
- **`docs/FOR-KENT.md`:** how to run it, what is durable and what is a prototype, the API, the permission conventions, what to watch (no real authentication, polling, server-side history), moving data from the artifacts, and the four decisions still open.
- **Design-system artifact:** the design system itself (`design-system/project/`) was not changed in these phases, so the published artifact needs no refresh. Scheduler-only, Fee Builder-only and Minutes-only tokens stay in each module's `ui/tokens.css` (the design system's README says to keep them there until a second app needs them; the three chart and brand marks that two apps share, such as `--g-blue`, are candidates to promote).
